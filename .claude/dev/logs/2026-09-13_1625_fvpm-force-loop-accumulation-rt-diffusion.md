# Task summary

Investigated the "switch RT gradient loop to type 2" option raised earlier for closing the same gather/union gap that Gizmo's gradient loop had, and worked out the alternative: accumulate the face-closure diagnostic (Sum_j A_ij, split into row-sum/column-sum terms) in the force/flux loop instead, which is already type-2/union for both RT and diffusion. Implemented it for RT in `swiftsim_fvpm_fix`. Specified (did not implement) the equivalent for the diffusion solver in the read-only `swiftsim_0` checkout. Updated `design_plan.tex` to record the investigation and decision.

# Decisions

- Gave RT its own `rt_area*` fields rather than reusing Gizmo's `area`/`area_sum1`/`area_sum2`, because `GIZMO_MFV_SPH` + `RT_GEAR` is a real, configure.ac-supported combination in which both loops run against the same struct.
- Chose to touch `src/rt/GEAR/rt.h` (three small additions: one `#include`, one reset call, one check call) even though the task named only `rt_iact.h` and `fvpm_geometry_struct.h` as in-scope files. Gizmo's equivalent check already had a call site (`hydro_end_gradient` already called `fvpm_check_total_face_area_vector_sum` before this task started); RT had no analogous call site anywhere, and the natural per-sub-cycle reset / per-transport-loop finalize hooks (`rt_reset_part_each_subcycle`, `rt_finalise_transport`) both live in `rt.h`, not `rt_iact.h`. Confirmed via `grep` that no other file currently includes `rt_iact.h` except the top-level `src/rt.h` dispatcher (which already includes both `rt/GEAR/rt.h` and `rt/GEAR/rt_iact.h` in that order), so adding the include inside `rt/GEAR/rt.h` introduces no circular dependency -- verified empirically by the full build succeeding.
- Did not gate the RT accumulation on `p->time_bin == 0` the way Gizmo's diagnostic does (Gizmo's own comment: "This only works for the idealised examples..."). RT's diagnostic is reset and checked per sub-cycle regardless of time-bin, so it stays usable outside single-global-timestep test setups.
- Added a compile-time gate, `FVPM_RT_FACE_CLOSURE_DIAGNOSTIC` (undefined by default), wrapping the new fields, the `A1`/`A2` computation, the accumulation, both new functions, and their call sites in `rt.h`. This was not in the first pass; the advisor review pointed out that the closure defect at an h-discontinuity (10-80% relative, per `fourth_attempt.tex`'s Table `tab:split`) is far above the 1e-2 warning threshold, so an ungated `warning()` would flood any real (non-idealised) RT run at every resolution change, every sub-cycle -- a log bomb, not a diagnostic -- and would also add unconditional per-pair work (ten float stores per side) to the RT flux hot loop in every build. Chose the compile-time-flag route over mirroring Gizmo's `time_bin == 0` gate, matching the branch's existing `FVPM_ATTEMPT1_FACE_RESCALING` precedent (`src/hydro/Gizmo/hydro_iact.h`) rather than inventing a new convention, and because it makes a default (flag-off) build provably identical to a build without any of this change (verified: no unused-variable warning on `A1`/`A2`, confirming full removal, not just dead code left for the optimizer). This decision landed after the RT implementation was otherwise complete and already build-verified; see Verification for the additional builds this required.
- Kept RT's ill-conditioned SPH-fallback branch's production `Anorm` expression byte-for-byte untouched, computing `A1`/`A2` alongside it purely for the diagnostic; documented in-code that `A1 + A2 != A` to rounding in that branch only (the well-behaved branch's split is bit-identical to the original combined expression, since IEEE negation and addition introduce no extra rounding for a two-term sum).
- Used a `git stash create` + `git worktree add --detach` snapshot to get an isolated, disposable build tree for verification, rather than reconfiguring the real checkout (which is set up for `gizmo-mfv` and has substantial other uncommitted/untracked work the task said not to disturb).

# Rejected alternatives

- Building a type-2 dispatcher for `task_subtype_rt_gradient` from scratch (the option the task explicitly asked to avoid): would be new, unproven machinery for a diagnostic that doesn't need it, since the force/flux loop is already type-2.
- Switching SPHENIX's own shared hydro gradient task to type 2: out of scope, huge blast radius, would affect all SPH physics.
- Routing RT's face computation through the shared `fvpm_compute_face_area_vector` (now available with the `A1`/`A2` signature after the Gizmo work) instead of keeping RT's own inline duplicate: would be a bigger behavioural change than asked for (touches RT's actual production flux path, not just the diagnostic), and is exactly the separate "de-duplicate" work item already on record in design_plan.tex (Stage 1 item 5) -- left alone.
- Gating diffusion's future accumulation on `both_updatable_here`/mode flags borrowed from RT's pattern: diffusion's own `update_left`/`update_right` parameters already encode exactly which side receives the flux for every one of its four decision-table cases (symmetric, nonsym-inactive-neighbour, mixed-depth-band, cross-rank), so no RT-style reconstruction is needed there -- recorded as the simpler, correct gate in the design write-up.
